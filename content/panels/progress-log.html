The diagnostic tool

diagnose_snapshot_columns.py — purpose: before designing signal↔background matching, establish ground truth about the snapshot schema. It reads snapshot files (.root via PyROOT/uproot, or .csv), classifies every column (label / weight / kinematics / region / NN-score / pass-flag / vertex / track-jet / trigger), computes the signal∩VR intersection, flags MC-only branches and dtype mismatches, parses the cutflow C++ source for the authoritative raw→scaled map and the cut sequence, and writes a JSON report. It modifies nothing.

What it found (baseline, post-NN snapshots)

  • Background (data24VR): events.root tree analysis, 474 columns.
  • Signal (mc23a mS35): 476 columns.
  • 456 shared; 20 signal-only (MC scale-factors / weights / sumOfWeights); 18 background-only (extra trigger branches from the looser data skim). No dtype mismatches.
  • 33 raw (*_raw) features — all 33 in the shared set. These are the token vocabulary. 50 scaled twins exist (config-dependent, avoid); 276 vector-typed branches incl. InputMapNN* (NN-internal plumbing, avoid).

Snapshot point — chosen and why

Key fact from the source scan: all 279 feature columns are .Defined before any filter, so the snapshot's column set is identical at every cut stage — moving the snapshot changes which rows survive, not which columns exist. So the design question is row-survival, not column availability. Decision: branch after "Passes Trigger" (stage 1 of 14); keep 1 MSVtx as a filter on the branch (per-vertex .at(0) indexing safety); convert every downstream cut (nMDT … NN2) to a pass_* boolean flag (no row drop); redirect the snapshot to that branch while leaving the original filtered chain intact so the cutflow Report/yields still reproduce Julian's reference. Branching before HTmiss keeps it un-applied so signal can be region-matched to the VR in Python on raw htmiss_NOSYS.

Data / background files in use

  • Signal MC (mc23a only — no mc23e exists, checked disk + CERNBox): DSIDs 537836 mS5 ct411, 537837 mS16 ct580, 537838 mS35 ct1310, 537839 mS55 ct1050. On disk at /data2/kjohns/run3_sample_ntuple_files/mc/HSS/.
  • Background VR (data24VR only — no data22/23 VR exists): 65 GB at /data2/kjohns/run3_sample_ntuple_files/data/data24/data24VR/.
  • Campaign mismatch: mc23a = 2022 conditions; data24 = 2024 (would be mc23e). ⟨μ⟩ ≈ 54 vs 64. Accepted as caveated exploratory. Mitigations: (a) pileup-reweight weighted MC to the data24 μ-profile; (b) μ-stability control in the grammar test. mc23e/data23VR production request declined for now.

Matching scheme — locked

  • Tokens = the 33 *_raw scalars (explicit allowlist, never "all numeric").
  • Label = file-of-origin (signal vs VR), not mcChannelNumber (MC-only).
  • Fit one frozen tokenizer on VR (or combined), transform both → token k means the same value on both sides. Pin the sklearn version (quantile edge default changes in 1.9).
  • Region-match on raw htmiss_NOSYS (VR is pre-skimmed < 40; cut signal to match).
